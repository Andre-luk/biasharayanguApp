1.Vue d'ensemble

Application Flutter multi-plateformes adossée à Supabase (PostgreSQL), avec une base locale SQLite faisant office de tampon hors connexion.

ÉlémentChoix retenuRaison
InterfaceFlutter (Dart), une seule base de code pour Android, iOS, Windows, Linux et Web.Un commerçant peut commencer sur téléphone et continuer sur un poste fixe sans second développement.
Navigationgo_router, routes déclarées dans lib/config/app_router.dart, middleware de permissions dans GoRouter.redirect.Un point unique de contrôle : la protection d'un écran est centralisée, pas dispersée.

Principes d'architecture tenus par le code

  1. Le client ne décide pas de ses droits. L'interface masque, le serveur refuse.
  2. Le public passe par des fonctions serveur, jamais par des tables. Aucun chemin direct vers une colonne privée.
  3. La base locale est un tampon, pas une vérité. Une donnée non synchronisée est identifiable (is_synced = 0).
  4. Chaque module ajoute, ne remplace pas. Les migrations sont additives et idempotentes.
  5. Tout échec est expliqué. Les messages d'erreur arrivent préfixés d'un code (CODE|texte français), traduit par la couche Dart.

Conventions à respecter pour toute évolution

  • lib/pages reste plat et en snake_case.
  • Un service expose un instance singulier et un type d'erreur métier (TypeErreurXxx) ; les messages serveur sont décodés, jamais affichés bruts.
  • Les modèles n'importent pas Flutter : ils doivent rester testables sans binding.
  • Ajouter une valeur à l'énumération PageAccess impose d'ajouter la case correspondante dans lib/widgets/icones_pages.dart — sans quoi le switch cesse d'être exhaustif et la compilation échoue.
  • Une carte d'accueil ajoutée change le nombre de cartes attendu dans test/accueil_modules_test.dart.

Conventions structurantes

  • Rattachement des données : la plupart des tables métier portent owner_id (l'espace de travail) ; espaces porte entreprise_id — c'est le pivot du cloisonnement.
  • Absence de owner_id sur espaces : le propriétaire est résolu par jointure sur utilisateurs (parent_id is null), évitant une donnée dupliquée qui pourrait se désynchroniser.
  • Colonnes de synchronisation : is_synced, updated_at, parfois deleted_at pour les suppressions douces.
  • Colonnes d'audit : created_at systématique ; moderation_note / moderation_le / moderation_par sur les publications (module 20).
  • Idempotence : chaque migration utilise if not exists, drop policy if exists, create or replace : elle peut être rejouée sans effet secondaire.

Deux migrations attendent une exécution manuelle

Le DDL n'est pas réalisable via l'API REST utilisée par l'application. Les migrations 20260916000040_module19_marketplace.sql et 20260916000041_admin_plateforme.sql doivent être exécutées dans l'éditeur SQL du projet. Tant qu'elles ne le sont pas, l'application fonctionne, mais les écrans concernés affichent un message explicite invitant à les installer — et refuse toute opération sensible plutôt que d'échouer silencieusement.

4.Rôles, permissions et RLS

Huit rôles

SUPER_ADMIN, GESTIONNAIRE_COMPTES, FINANCE_LAPERLE, SUPPORT (plateforme) ; PROPRIETAIRE, VENDEUR, MAGASINIER, COMPTABLE_ENTREPRISE (entreprise).

Trois niveaux de contrôle

NiveauOùRôle
NavigationPermissionService.routeAutorisee() dans le redirect du routeur.Empêche l'ouverture d'un écran interdit, même par URL directe.
InterfacePermissionGate, CarteAccueil.visibles().N'affiche que les actions possibles : cohérence perçue par l'utilisateur.
ServeurRLS PostgreSQL + contrôles dans chaque fonction security definer (est_plateforme(), mon_proprietaire(), a_permission()).Seul niveau réellement opposable à un client modifié.

Point de vigilance structurel

routeAutorisee() retourne true lorsqu'aucune règle ne correspond à l'URL. C'est ce qui rend les routes publiques possibles (/biashara*), mais cela signifie aussi qu' une nouvelle route sensible doit être ajoutée à la liste des règles dans lib/services/permission_service.dart — sinon elle est ouverte par défaut côté navigation (le serveur restant, lui, protecteur).

RLS : ce qui est réellement exposé

  • Le rôle anon ne possède aucun privilège sur les tables du module marketplace.
  • La vue v_biashara_boutiques est révoquée pour public, anon et authenticated : elle n'est utilisable qu'à l'intérieur des fonctions serveur.
  • Les tables de gestion (ventes, clients, dettes, dépenses, stock) sont filtrées par appartenance à l'entreprise.
  • Les écritures du module marketplace passent par des fonctions qui revérifient la propriété : les insert/update directs sont retirés aux rôles concernés.

5.Synchronisation et mode hors connexion

Mécanisme

  1. L'écriture se fait d'abord en local (SQLite) avec is_synced = 0 : l'utilisateur n'attend jamais le réseau.
  2. SyncService pousse les lignes non synchronisées vers Supabase, puis les marque is_synced = 1.
  3. Les modifications provenant d'autres appareils arrivent par Realtime (onPostgresChanges) et sont appliquées localement.
  4. Un mécanisme de déduplication (_seenRealtimeEvents, plafonné) évite de réappliquer deux fois le même événement.
  5. Les appels réseau passent par une reprise limitée (_withRetry) avant d'abandonner.

Gestion des conflits

Résolution « dernière écriture gagnante » avec heuristiques : une écriture locale plus récente que la version serveur est conservée ; une ligne locale non synchronisée n'est pas écrasée ; un stock serveur inférieur au stock local est ignoré. C'est suffisant pour un usage mono-boutique à faible concurrence, mais ce n'est pas une résolution transactionnelle : voir la dette technique en section 10.

Limites connues

LimiteConséquenceContournement

6.Marketplace géolocalisée

Architecture : liste blanche

Visiteur (anon)  →  fonction serveur "security definer"  →  vue v_biashara_boutiques (colonnes publiques)
                                                         ↘  tables internes : INACCESSIBLES

Aucune requête du catalogue public ne lit une table directement. Une vingtaine de fonctions exposent une liste blanche de colonnes : nom, description, contacts publics, horaires, adresse, position, prix public, disponibilité déclarée. Les prix d'achat, les quantités exactes, les clients et les dettes ne sont pas atteignables.

Distances et position

  • public.distance_km(lat1, lng1, lat2, lng2) : Haversine pur SQL, immuable, testable.
  • public.biashara_tranche_distance(km) : convertit une distance en tranche statistique (<1, 1-3, 3-10, >10) — c'est ce qui est stocké, jamais la distance exacte.
  • La position du visiteur est conservée en mémoire dans le service, le temps de la session, et n'est jamais envoyée au serveur.
  • Côté commerçant, la position est confirmée par un acte explicite : statut_localisation = 'verifiee', sinon 'a_verifier'.

      + 5 si position confirmée
  (aucun critère de taille, d'ancienneté ou de chiffre d'affaires)

Quatre catégories d'événements

Attribution

La table liens_attribution génère des codes de la forme BIA-XXXXXX (QR de vitrine, lien de suivi, code promotionnel). Une conversion n'est comptée que lorsqu'un de ces codes est effectivement utilisé : une simple consultation n'est jamais convertie en vente. L'intégration au module d'encaissement n'a volontairement pas été modifiée : elle fera l'objet d'une évolution dédiée afin de ne prendre aucun risque sur le chemin de vente existant.

Publicité

  • Cycle de vie : brouillon → soumise → active → terminee, avec pause et refusee.
  • Seule la plateforme active ou refuse ; le commerçant soumet, met en pause et termine.
  • Ciblage : ville, quartier, rayon autour d'un point, catégorie. Un ciblage « quartier » ne bloque pas l'affichage faute d'information côté visiteur — choix documenté dans le code.
  • Mention « PUBLICITÉ » portée par le widget d'affichage lui-même, pour ne jamais dépendre de l'écran appelant.
  • Compteurs : impressions, clics, conversions, avec plafond d'impressions.

Accessibilité

  • Échelle de texte configurable dans Réglages, appliquée à toute l'application, dialogues compris.
  • Les grilles utilisent désormais une proportion calculée à partir de cette échelle : plus de débordement quand le texte est agrandi.
  • Thème clair et thème sombre pris en charge par le gestionnaire de thème.

Internationalisation : état réel

L'infrastructure existe (fichiers ARB, délégués, gestionnaire de langue), mais seules 26 clés sont traduites alors que l'interface est en français quasi intégralement. Après l'audit, seules les locales réellement traduites sont déclarées et les autres sont présentées comme « en préparation » : plus de promesse trompeuse. L'externalisation complète reste un chantier identifié (section 10).

9.Migrations et déploiement

Procédure d'application d'une migration

  1. Ouvrir l'éditeur SQL du projet Supabase.
  2. Coller le contenu du fichier de migration et l'exécuter. Les migrations sont idempotentes : une réexécution est sans effet.
  3. Lire les requêtes de vérification placées en fin de fichier : elles retournent des compteurs attendus (tables créées, colonnes présentes, pages de permission déclarées).
  4. Vérifier dans l'application que l'écran concerné charge sans message d'installation manquante.

Ne pas compiler localement sur la machine de développement

La compilation d'un paquet Android sur le poste de développement actuel sature la mémoire de la machine. La validation se fait donc par l'analyse statique et les tests ; la production des paquets est déléguée à l'intégration continue (déclenchement par étiquette de version ou manuel).

Publication

  • La version applicative est déclarée dans pubspec.yaml et rappelée dans la page « À propos ».
  • Signature Android : tools/setup_signature.sh ; le fichier de clés n'est jamais versionné (key.properties.example sert de modèle).
  • Déploiement de la fonction d'assistant : tools/deploy_agent_ia.sh.
  • Procédure de publication détaillée : docs/publication_app.md ; sauvegarde et restauration : docs/backup_restore_supabase.md.

Dette technique identifiée (non corrigée, assumée)

SujetÉtatRecommandation
Uniformisation visuelle des anciens écrans Une centaine de pages utilisent encore des couleurs codées en dur et un indicateur de chargement nu. Migration progressive vers AppCouleurs et ModernLoader, module par module, en commençant par les écrans les plus utilisés (accueil, caisse, collaborateurs).
Internationalisation 26 clés traduites sur trois langues annoncées. Soit externaliser progressivement, soit maintenir l'anglais et le swahili désactivés (état actuel) jusqu'à traduction effective.
Journalisation de développement Environ 390 appels de journalisation sans garde de mode. Encadrer par un contrôle de mode debug lors d'une passe dédiée.
Écrans d'administration historiques La sauvegarde/restauration et la gestion des catégories s'appuient sur la base locale SQLite, ce qui peut donner l'impression d'une sauvegarde serveur. Rendre explicite la portée réelle (locale) et renvoyer vers docs/backup_restore_supabase.md pour la sauvegarde serveur.
Résolution de conflits de synchronisation Heuristiques « dernière écriture gagnante ». Suffisant en usage mono-boutique ; prévoir un numéro de version par ligne si la concurrence multi-poste s'intensifie.
Notifications entre appareils Absentes (nécessiterait un canal par boutique). À planifier si plusieurs personnes doivent être alertées en temps réel.
Attribution des conversions à la caisse Les codes d'attribution sont enregistrés mais ne sont pas encore consommés par le module de vente. Évolution dédiée, à mener sans modifier le chemin de vente existant sans tests d'accompagnement.
